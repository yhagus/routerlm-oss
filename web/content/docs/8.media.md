# Images, audio and video

Besides chat, a Model has one of four media Kinds. Each Kind has its own endpoints, in the format of the matching official SDK client (`client.images`, `client.audio` and `client.videos`):

| Kind | Endpoints |
| --- | --- |
| `image` | `POST /v1/images/generations`, `POST /v1/images/edits` |
| `speech` | `POST /v1/audio/speech` |
| `transcription` | `POST /v1/audio/transcriptions` |
| `video` | `POST /v1/videos`, `GET /v1/videos/{id}`, `GET /v1/videos/{id}/content` |

[`GET /v1/models`](/docs/models) gives each Model's `kind`. A Model sent to an endpoint of another Kind, such as an image Model on `/v1/chat/completions` or a chat Model on `/v1/images/generations`, gets `400 invalid_request`, and the message names both Kinds.

These endpoints authenticate and fail like the chat endpoints (see [Authentication](/docs/authentication) and [Errors](/docs/errors)). Their errors use the Chat Completions error body. The gateway always returns the generated bytes itself, never a link to where they were made.

A JSON body may be at most 20 MB. In a multipart form, each uploaded file may be at most 25 MB. A larger one gets `413 request_too_large` before anything is sent on.

The JSON blocks below show request bodies and responses. Send them with any HTTP client, with the API Key in the `Authorization` header.

## Generating images

`POST /v1/images/generations` takes a JSON body:

```json
{
  "model": "my-image-model",
  "prompt": "A lighthouse at dawn, watercolor",
  "n": 2,
  "size": "1024x1024"
}
```

| Field | Meaning |
| --- | --- |
| `model` | Required. A Model of the `image` Kind. |
| `prompt` | Required. What to draw. |
| `n` | How many images, from 1 to 10. The default is 1. |
| `size` | `WIDTHxHEIGHT`, such as `1024x1024`, or `auto` to let the Model choose. If no Route of the Model can produce the size, the request gets `400 no_capable_route` naming it. |
| `negative_prompt` | What the image should not show. |
| `seed` | An integer from 0 to 2147483647, for repeatable results. |

The response holds every image as base64 in `b64_json`:

```json
{
  "created": 1794700000,
  "data": [{ "b64_json": "iVBORw0KGgo..." }, { "b64_json": "iVBORw0KGgo..." }]
}
```

These get `400 invalid_request`:

- `response_format` other than `b64_json`. The gateway never returns image URLs.
- `stream`, and `partial_images` other than 0.

## Editing images

`POST /v1/images/edits` takes the same fields as a generation, plus the input images to start from: at least 1 and at most 16. Send them in one of two ways:

- **JSON:** an `images` array of `{ "image_url": "..." }` objects. Each `image_url` is an `https://` or `http://` URL, or a `data:image/...;base64,...` URL.
- **Multipart form:** each image uploaded as a file in the `image` field (one image) or the `image[]` field (several), with the other fields as form fields. This is what the SDKs send.

```json
{
  "model": "my-image-model",
  "prompt": "Put the cat on the sofa",
  "images": [
    { "image_url": "https://example.com/cat.png" },
    { "image_url": "https://example.com/sofa.png" }
  ]
}
```

A Model's Routes may take fewer input images than 16. More input images than any Route takes gets `400 no_capable_route`, and the message gives the limit. A `mask` gets `400 invalid_request`, and so does an uploaded file that is not an image. The response is the same as a generation's.

## Speech

`POST /v1/audio/speech` turns text into audio:

```json
{
  "model": "my-speech-model",
  "input": "Your order has shipped.",
  "voice": "my-voice",
  "response_format": "mp3"
}
```

| Field | Meaning |
| --- | --- |
| `model` | Required. A Model of the `speech` Kind. |
| `input` | Required. The text to speak. |
| `voice` | Required. Passed on unchanged, so it must be a voice the Model's upstream knows. Ask the gateway's operators which voices a Model has. An operator's setting for the Model can force a voice, and it wins over yours. |
| `response_format` | `mp3` (the default), `wav`, `pcm` or `opus`. |
| `speed` | From 0.25 to 4. |
| `instructions` | Accepted, but not sent on: it has no effect yet. |

The response body is the audio itself, with the content type of its format: `audio/mpeg`, `audio/wav`, `audio/pcm` or `audio/opus`.

These get `400 invalid_request`:

- Any other `response_format`, such as `aac` or `flac`. The gateway never converts audio to a format you didn't ask for.
- `stream_format` other than `audio`. Speech doesn't stream yet.

## Transcription

`POST /v1/audio/transcriptions` turns audio into text. It takes a multipart form with these fields:

| Field | Meaning |
| --- | --- |
| `file` | Required. The audio file, at most 25 MB: aac, amr, flac, m4a, mp3, mp4, mpeg, ogg, opus, wav or webm. The gateway reads the format from the file's content type, or from its file name when the type is generic, such as `application/octet-stream`. |
| `model` | Required. A Model of the `transcription` Kind. |
| `language` | The spoken language, such as `en`, as a hint for recognition. |
| `response_format` | `json` (the default) or `text`. |

With `json`, the response gives the transcript and the length of the audio in seconds:

```json
{
  "text": "Your order has shipped.",
  "usage": { "type": "duration", "seconds": 2 }
}
```

With `text`, the response body is the transcript alone, as `text/plain`.

These get `400 invalid_request`:

- Any other `response_format`, such as `srt`, `vtt` or `verbose_json`. They need timestamps the gateway doesn't return yet.
- `stream` set to `true`.
- A file whose format the gateway can't tell, or that isn't audio.

The gateway ignores `prompt`.

## Videos

A video takes minutes to make, so you start a Video Job, poll it, and download it once it is done.

### Starting a Video Job

`POST /v1/videos` takes a JSON body, or a multipart form with the first frame uploaded as a file in the `input_reference` field:

```json
{
  "model": "my-video-model",
  "prompt": "A red fox runs through snow",
  "seconds": "5",
  "size": "1280x720"
}
```

| Field | Meaning |
| --- | --- |
| `model` | Required. A Model of the `video` Kind. |
| `prompt` | Required. What happens in the video. |
| `seconds` | The length, a positive whole number, as a number or a string. The default is 5. `-1`, which leaves the length to the upstream, gets `400 invalid_request`: the gateway must know the length when the job starts. |
| `size` | `WIDTHxHEIGHT` in an aspect ratio of 16:9, 9:16, 1:1, 4:3 or 3:4, such as `1280x720`. Its shorter side picks the nearest resolution: 480P, 720P or 1080P. |
| `resolution` and `aspect_ratio` | Instead of `size`: `480p`, `720p` or `1080p`, and one of the aspect ratios above. Send either `size` or these, not both. Without any of them, the video is 720P. |
| `seed` | An integer from 0 to 2147483647. |
| `input_reference` | The first frame: `{ "image_url": "..." }`, or an uploaded file in a multipart form. |
| `frame_images` | A first or last frame, or both: objects with a `frame_type` of `first_frame` or `last_frame` and an `image_url`. |
| `input_references` | Reference images that guide the video: objects with an `image_url`. |

Each `image_url` is an `https://` or `http://` URL, or a `data:image/...;base64,...` URL. It may also be written as `{ "url": "..." }`, and an object may carry `"type": "image_url"`.

Send one first frame at most, in either `input_reference` or `frame_images`, and one last frame at most. With a first frame, the video takes the first frame's aspect ratio.

```json
{
  "model": "my-video-model",
  "prompt": "The fox turns toward the camera",
  "frame_images": [
    { "type": "image_url", "frame_type": "first_frame", "image_url": "https://example.com/start.png" },
    { "type": "image_url", "frame_type": "last_frame", "image_url": "https://example.com/end.png" }
  ]
}
```

What a request starts from decides which Routes can serve it. Each needs its own capability: `text-to-video` for a prompt alone, and `first-frame`, `last-frame` or `reference-images` for each kind of image you send. A request that no Route of the Model can serve gets `400 no_capable_route`, naming what is missing: a capability, a resolution, a length outside every Route's range, or more input images than a Route takes.

The response is a video object with status `queued`. Keep its `id`:

```json
{
  "id": "video_...",
  "object": "video",
  "status": "queued",
  "model": "my-video-model",
  "seconds": "5",
  "size": "1280x720",
  "created_at": 1794700000
}
```

`size` is the `size` you sent, or `null` when you sent `resolution` and `aspect_ratio`.

### Polling a Video Job

`GET /v1/videos/{id}` answers with the same video object and its current `status`: `queued`, `in_progress`, `completed`, `failed` or `expired`. A finished job also has `completed_at`, when the upstream reports it. A failed job has an `error` with the code `video_generation_failed`.

### Downloading the video

Once `status` is `completed`, `GET /v1/videos/{id}/content` streams the video as `video/mp4`. Before then, it gets `409 video_not_ready`.

A video id works only with the API Key that started the job. Polling or downloading with an id the gateway didn't issue to your API Key, or a job that expired, gets `404 video_not_found`. A job that expired can't be downloaded again: start a new one.
